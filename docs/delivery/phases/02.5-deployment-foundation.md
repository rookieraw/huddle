# Phase 2.5 — CI/CD and Deployment Foundation

Status: Planned  
Depends on: Phase 2 — Contacts and Chat  
Next gate: Phase 3 — Voice and Video Calling

## Objective

Establish automated validation and a reproducible OCI deployment foundation before introducing WebRTC media infrastructure.

This is an engineering and delivery gate. It must not introduce new product capabilities.

## Implementation Authority

Phase 2.5 may change:

- Build and test configuration
- CI workflows
- Container definitions
- Deployment configuration
- Environment templates
- Health and readiness endpoints
- Engineering documentation
- Operations documentation

It must not implement Phase 3 or later product behavior.

Detailed implementation and operational instructions belong to the relevant Engineering and Operations documents. This file defines only the authorized Phase 2.5 scope and its completion gate.

## Required Deliverables

### Continuous Integration

Automated validation must cover:

- Dependency installation from the committed lockfile
- Formatting verification
- Linting
- Type checking
- Unit tests
- Integration tests
- Production application builds
- Migration validation
- Container-image build validation

A required validation failure must fail the workflow.

CI must not use production credentials or depend on a publicly deployed Huddle environment.

### Integration-test Infrastructure

Automated integration tests must provide isolated dependencies for:

- PostgreSQL
- MongoDB
- Redis

Test setup and cleanup must be deterministic.

Concurrency behavior that depends on PostgreSQL transactions or constraints must be tested against PostgreSQL rather than an in-memory substitute.

MongoDB indexes and persistence behavior must be tested against MongoDB rather than repository mocks alone.

### Coverage Baseline

Phase 2.5 establishes the first measured coverage baseline after Chat is implemented.

The project must:

1. Measure the actual baseline.
2. Document justified exclusions.
3. Prevent unexplained regression.
4. Raise thresholds as tested behavior grows.

Coverage percentages do not replace explicit testing of:

- Domain invariants
- Authorization
- Concurrency
- Idempotency
- Persistence constraints
- Failure translation
- Cross-context boundaries

Detailed coverage policy belongs to `engineering/testing.md`.

### ARM64 Application Images

Production-oriented application images must build for the target OCI architecture:

```text
linux/arm64
```

The images must provide:

- Reproducible dependency installation
- Explicit startup behavior
- Predictable shutdown behavior
- Health-check support
- Traceable image versions
- No embedded secrets

A non-root runtime user and production-only runtime dependencies should be used where supported.

This phase validates the Phase 2 application stack on ARM64. mediasoup and coturn validation belong to Phase 3.

### Docker Compose Foundation

The baseline deployment uses Docker Compose on one Linux host.

The Phase 2.5 deployment may include:

- Reverse proxy
- Next.js application
- NestJS API Gateway
- PostgreSQL
- MongoDB
- Redis
- A worker process only when an implemented Phase 2 capability requires one

The executable Compose configuration is the source of truth for service definitions.

It must define the required:

- Internal networking
- Persistent storage
- Health checks
- Restart behavior
- Environment injection
- Startup dependencies
- Resource-conscious defaults

Documentation must explain how to operate the configuration without duplicating its complete contents.

### OCI Deployment Foundation

The target environment is an OCI Always Free Ampere A1 Linux VM.

Phase 2.5 must establish enough infrastructure to deploy and operate the Phase 2 application, including:

- Host access
- Container runtime
- Public application ingress
- DNS and HTTPS
- WebSocket forwarding
- Persistent storage
- Deployment configuration
- Application logs
- Restart and rollback procedures

The environment remains a low-traffic portfolio deployment.

It must not claim:

- High availability
- Production SLA
- Zero-downtime deployment
- Horizontal scaling
- Multi-region resilience

Exact infrastructure and network procedures belong to `operations/deployment.md`.

### Network Boundary

Public ingress during Phase 2.5 is limited to the Phase 2 web application, API, WebSocket, and restricted administration requirements.

The following services must not be publicly exposed:

- PostgreSQL
- MongoDB
- Redis
- Internal NestJS ports
- Container-management interfaces

mediasoup and coturn network exposure belongs to Phase 3.

Exact ports and firewall rules belong to `operations/deployment.md`.

### HTTPS and WebSocket Validation

The deployed Phase 2 system must demonstrate:

- Valid HTTPS
- HTTP-to-HTTPS redirection
- Application health response
- Next.js application delivery
- WebSocket upgrade through the reverse proxy
- Authenticated socket connection
- Unauthorized socket rejection
- Message send and receive
- Socket reconnection
- Production CORS and origin enforcement

Local success alone is not deployment evidence.

### Configuration and Secrets

Configuration must distinguish:

- Local development
- Automated tests
- Portfolio deployment

Secret values must not be committed or embedded in images.

Committed environment templates may contain variable names and safe descriptions only.

The deployed application must not silently fall back to development credentials or signing secrets.

Detailed secret-handling rules belong to `architecture/security.md` and `operations/deployment.md`.

### Persistent Data

PostgreSQL and MongoDB must use persistent storage.

Phase 2.5 must provide:

- Schema migration execution
- MongoDB index initialization
- Startup failure when required persistence is unavailable
- Documented backup preparation
- Documented restore outline
- Persistence across container recreation

The complete backup-and-restore exercise is required before Portfolio Release.

Redis remains reconstructable infrastructure state. Durable domain data must not exist only in Redis.

### Repeatable Deployment and Rollback

The Phase 2 application must be deployable from committed configuration plus externally supplied secrets.

The deployment must have documented procedures for:

- Host preparation
- Configuration supply
- Migration execution
- Application startup
- Health verification
- HTTPS and WebSocket verification
- Rollback to a known application version

Rollback planning must account for migration compatibility. It must not assume that every database migration is automatically reversible.

The executable steps and actual automation level belong to `operations/deployment.md` and `operations/runbook.md`.

### Automation Security

CI and deployment automation must follow least privilege.

Required safeguards include:

- Protected secret storage
- No secret values in logs
- Restricted deployment credentials
- Explicit deployment-environment selection
- Lockfile enforcement
- Reviewable workflow configuration
- No use of production credentials by untrusted pull-request code

## Required Evidence

Phase 2.5 must produce evidence for:

- Clean dependency installation
- Required CI failure detection
- PostgreSQL integration testing
- MongoDB integration testing
- Redis-dependent integration testing
- Production application builds
- ARM64 image builds
- Container startup and readiness
- Migration execution
- Persistent data after container recreation
- HTTPS
- Authenticated WebSocket messaging
- Unauthorized WebSocket rejection
- Application restart
- Deployment rollback

Evidence may be an automated test, CI result, deployment observation, or documented operational exercise, depending on the capability.

## Definition of Done

Phase 2.5 is complete only when:

- Required CI checks run automatically.
- A verified coverage baseline exists.
- Unexplained coverage regression is blocked.
- Required integration tests run against real datastores.
- Production application builds succeed.
- Application images build for ARM64.
- Docker Compose starts the Phase 2 stack.
- PostgreSQL and MongoDB data survive container recreation.
- OCI successfully hosts the Phase 2 application.
- HTTPS and WebSocket work through the deployed reverse proxy.
- Persistence services are not publicly exposed.
- Secret handling is documented.
- Deployment and rollback procedures are documented and exercised.
- `operations/deployment.md` reflects the executable deployment.
- `operations/runbook.md` covers relevant failure and recovery procedures.
- `delivery/status.md` reflects the completed gate.

## Explicitly Deferred

Phase 2.5 must not add:

- Voice or video calls
- WebRTC signaling
- mediasoup
- coturn
- Media transport ports
- Stripe checkout
- Stripe webhooks
- Billing persistence
- Standalone Meetings
- Notification delivery
- Kubernetes
- Multiple application hosts
- Independent microservices
- Multi-region deployment
- Production SLA claims
